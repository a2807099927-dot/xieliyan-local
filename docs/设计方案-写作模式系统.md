# 写梨眼 Agent：写作模式系统（新书创作 / 老书续写）—— 模块设计方案 v3

> 版本：v3（2026-08-03）
> 性质：模块设计方案（从创作状态划分模式）
> 核心句：**新书模式负责从 0 建立确定性；老书模式负责从已有信息恢复确定性。**
> 完整写前链路：确认设定 → 写法决策 → 同题材研究 → 剧情规划 → 大纲 → 大纲有效性审查 → 章节写作

---

## 1. 模块定位

一句话：**根据作品的创作状态，选择不同的创作模式。**

创作状态只有两种：
- **确定性不足**（新书）：用户只有一个想法，信息不够，需要 Agent 帮他把未知变成确定
- **确定性已有但 Agent 不懂**（老书）：用户有完整世界，风险是 Agent 不懂书、续跑偏

模块的价值不是「写」，而是 **Agent 动笔前的状态识别 + 信息获取 + 决策形成**。

---

## 2. 两种模式定义

### 2.1 新书创作模式（决策流程，不是写作流程）

**解决问题**：不知道写什么（信息从无到有）
**输入**：一句想法（可能只有「玄幻、穿越、有系统」）
**输出**：可写的作品骨架 + 已验证的大纲（方向定了、结构定了、爽点定了、大纲有效）
**本质**：决策流程——每一步都是「未知 → 确定」的转化，且必须用户参与

```
想法（一句）
   │
   ▼
① 方向探索 —— 生成 3 个方向卡
   方向A：《xxx》定位/核心卖点/适合读者/走向/风险
   方向B：…
   方向C：…
   │ 用户选一个 / 提出修改
   ▼
② 故事核心档案 —— 把选中的方向固化成五要素
   主角 / 世界 / 核心冲突 / 长线目标 / 爽点模型
   │ 用户确认
   ▼
③ 写法决策 —— 想清楚「怎么写、为什么这么写」
   叙事视角 / 节奏基调 / 差异化打法 / 读者定位
   │ 用户确认
   ▼
④ 同题材研究 —— 搜索同题材优秀作品，得出初步结论
   别人怎么开篇 / 核心爽点在哪 / 常见套路 / 本书差异化空间
   │ （产出研究结论卡，标注来源，防编造）
   ▼
⑤ 剧情规划 —— 规划剧情走向（分卷分阶段）
   第一卷目标 / 卷内冲突递进 / 主要角色弧线
   │ 用户确认
   ▼
⑥ 写大纲 —— 章节级大纲
   每章：核心事件 / 节拍 / 承担的剧情功能
   │ 用户确认
   ▼
⑦ 大纲有效性审查 —— 逐章审查「这段剧情有效还是无效」
   有效：推进主线 / 塑造人物 / 兑现爽点 / 制造冲突
   无效：注水 / 重复 / 无用功 / 偏离目标 → 标记并修改
   │ 用户确认调整后的大纲
   ▼
⑧ 章节写作 —— 细纲 → 写前复盘 → 正文 → review
```

**关键**：新书模式的每一步产出都先给用户看、用户点头才进下一步。模型不做静默决策。

### 2.2 老书续写模式（理解流程）

**解决问题**：不知道怎么接（信息已有，Agent 要先懂书）
**输入**：已有文本 + 剧情档案
**输出**：符合原书的续章
**本质**：理解流程——先恢复确定性，再续写；确定性恢复后走轻量链路

```
已有文本
   │
   ▼
① 读取 —— 前 8 章剧情档案 + 近 2 章正文（token 友好）
   │
   ▼
② 建模 —— 组装「书的理解」：
   世界规则（book.settings / worldSettings）
   人物档案（roleCard + archiveRecords 聚合）
   剧情状态（memoryBank 章梗概：已发生/当前/未收线头）
   风格模型（风格分析器：语言/节奏/叙事）
   注：全部来自已有数据，0 额外模型调用，不重造
   │
   ▼
③ 对齐 —— 首次建模 / 关键状态变更时，向用户展示：
   「我理解你的书目前状态如下：…」
   用户确认 / 纠正（仅此一次，后续续写不再重复确认）
   │
   ▼
④ 规划 —— runPlanning（必含节拍/禁止动作）+ 写前复盘（承接/怎么写/为什么/爽点）
   │
   ▼
⑤ 续写 —— 正文生成 → 写后 review
```

**扩展**：老书写**新卷 / 大情节转折**时，可选择性启用 ③④⑤⑥⑦（写法决策 → 同题材研究 → 剧情规划 → 大纲 → 大纲审查），避免新卷跑偏；日常续写不启用，保持轻量。

**关键**：老书模式的重心在 ①②③（理解与对齐），④⑤ 是已有链路。

## 3. 核心能力（6 项）

| 能力 | 说明 | 现状 |
|---|---|---|
| C1 作品状态识别 | 判断创作状态：新书（无实质正文）/ 老书（有正文） | `bookHasNoSubstantialBody` 已有，复用 |
| C2 上下文建立 | 新书=设定卡+题材打法；老书=档案+正文+风格模型 | 一半已有，需按模式组装 |
| C3 写前决策 | 方向卡 / 故事核心档案 / 写法决策 / 写前复盘卡——决策全程可见 | 写前复盘已有；方向卡、档案、写法决策新增 |
| C4 同题材研究 | 自主搜索同题材优秀作品 → 研究结论（开篇/爽点/套路/差异化） | **接线为主**：`web_search` 命令已有（Rust 爬 Bing），需注册进 Agent 工具；研究 prompt 新增 |
| C5 大纲生成与有效性审查 | 章节级大纲 + 逐章审查剧情有效/无效 | 大纲体系部分已有（plotOutline/formalize）；**有效性审查新增** |
| C6 章节生成 | 细纲 → 写前复盘 → 正文 → review 的完整产出链 | 已有，微调 |
| C7 Agent 看章节 | 自主打开小说站页面、提取正文/简介，供同题材研究深化 | **新增**（novel_browser 内嵌浏览器已有，需封装 Agent 工具 + 反爬适配） |

新增量集中在：**方向探索（C3）+ 故事核心档案（C3）+ 写法决策（C3）+ 同题材研究（C4）+ 大纲有效性审查（C5）**。其余是接线。

## 4. 用户体验流程（模块成型后）

### 新书案例
```
用户：我要写一本玄幻，主角穿越，有系统。
Agent：检测到新书 → 进入创作模式
  ├─ 卡片1：三个开局方向（卖点/走向/风险）
用户：选 A，但主角别一开始就无敌
Agent：
  ├─ 卡片2：故事核心档案（主角/世界/核心冲突/长线目标/爽点模型）——已按你的意见调整
用户：确认
Agent：
  ├─ 卡片3：写法决策（视角/节奏/差异化/读者定位）
用户：确认
Agent：
  ├─ 卡片4：同题材研究结论（同类书怎么开篇、爽点在哪、本书差异化空间）★
用户：确认
Agent：
  ├─ 卡片5：剧情规划（第一卷目标/冲突递进/角色弧线）
用户：确认
Agent：
  ├─ 卡片6：章节大纲（每章核心事件/节拍/功能）
用户：确认
Agent：
  ├─ 卡片7：大纲审查结果（第X章剧情无效→已改：…）★
用户：确认
Agent：
  ├─ 卡片8：写前复盘（第一章怎么打）
  ├─ 正文产出 → review → 交稿
```

### 老书案例（首次）
```
用户：继续写第50章
Agent：检测到老书 → 进入续写模式
  ├─ 读取：前8章档案 + 近2章正文
  ├─ 卡片：我理解你的书目前状态如下（世界/人物/剧情/风格）
用户：确认（或纠正）
Agent：
  ├─ 写前复盘（第50章承接/怎么写/爽点）
  ├─ 正文产出 → review → 交稿
```

### 老书案例（后续）
```
用户：继续
Agent：直接续写（上下文模型已建立，不再重复确认）
  ├─ 写前复盘 → 正文 → review
```

## 5. 验收标准

### G1 理解正确（老书不跑偏）
- [ ] 老书续写前，Agent 展示的「书的理解」与档案一致，无编造
- [ ] 首章建模确认一次后，后续续写不重复确认
- [ ] 续章承接点、人物状态、未收线头与档案对齐，无跳戏

### G2 决策透明（Agent 不黑盒）
- [ ] 新书：方向卡 → 核心档案 → 写法决策 → 研究结论 → 剧情规划 → 大纲 → 大纲审查 → 复盘卡，每一步用户可见可改
- [ ] 老书：复盘卡可见（承接/怎么写/为什么/爽点）
- [ ] 模型不做静默决策，新书每步产出都经用户确认

### G3 生成可靠（真正能写）
- [ ] 新书：从一句想法到第一章全链路走通，无「缺少细纲」类卡死
- [ ] 老书：续写正常产出，硬伤自动修订一次
- [ ] 解析失败一律降级不抛错；全量测试绿

### G4 大纲有效（新增，对应「剧情有效还是无效」）
- [ ] 大纲审查能标记出无效剧情（注水/重复/偏离目标），并给出修改
- [ ] 审查标准明确：有效 = 推进主线/塑造人物/兑现爽点/制造冲突
- [ ] 审查结果用户可确认、可否决，不自动覆盖大纲

### G5 研究可信（新增，对应「搜索同题材」）
- [ ] 同题材研究结论有来源标注（搜到的书/链接，或「基于训练知识，非实时」）
- [ ] 不编造「市场流行 X」式无来源断言
- [ ] 研究结论能落到本书差异化（不只是「别人怎么写」，还有「本书怎么不同」）

## 6. 边界与已定项

- **同题材研究已定：方案 C（自主联网搜索），且已有地基**
  - 写梨眼已内置 `web_search` 命令（`src-tauri/src/commands/ai/web_search.rs`）：Rust reqwest 爬 cn.bing.com 结果页，无需 API Key，返回前 5 条标题+摘要；已在前端多处可 invoke，但**尚未暴露给 Agent 工具**
  - **P 落地路径（接线为主）**：在 `agentToolRegistry` 注册 `web_search` 工具（unified loop 内直接 invoke），与 `read_url` 并列；Agent 在「同题材研究」环节自主调用：`web_search("玄幻 穿越 系统 经典 完本")` → 对命中的书再用 `read_url` 读书评/简介页深化
  - **增强（可选，后续）**：现有实现只爬 Bing 结果页。若命中质量不足，可扩展为「Bing 结果 + 命中书目的简介页抓取」两级，仍不需要浏览器驱动
  - 与「调用用户浏览器」的关系：写梨眼是 Tauri + Rust reqwest 栈，非 Hermes 浏览器栈；自主搜索 = reqwest 模拟搜索请求（带浏览器 UA），不等同驱动用户浏览器进程。效果一致（Agent 自主拿到搜索结果），工程上是现有命令接线，不是新造浏览器自动化
- **搜索结论防编造**：web_search 结果原文标注「【联网搜索结果（Bing）：<query>】」来源前缀；研究结论卡必须引用来源或标注「基于训练知识，非实时」，不输出无来源断言

- **Agent 看章节（C7）——已实地调研三站（2026-08-03 实测），**决策：只做笔趣阁系等公开低反爬免费站**，番茄/起点不做**：

  | 站 | URL 结构 | 正文 DOM | 反爬 | 实测结论 |
  |---|---|---|---|---|
  | 笔趣阁系 | 详情 `/look/{id}/`，正文 `/book/{id}/{n}.html` | `#chaptercontent` 容器，正文干净 | 低（仅常规 UA 检测） | ✅ **做**：novel_browser 打开 → execute_js 取 `#chaptercontent`.innerText，直接可用 |
  | 番茄 | 书页 `/page/{bookId}`，阅读 `/reader/{chapterId}` | 正文 `<p>` 段 | **字体加密**：常用汉字映射到 Unicode 私用区（实测正文全乱码如「乾皇朝」→「\ue063皇朝」），靠前端字体渲染 | ❌ **不做**：需字体映射表或 OCR，工程量大且易随站更新失效 |
  | 起点 | www.qidian.com | 需登录 | **安全检测**：直接弹验证码（实测「安全检测中」拦截页） | ❌ **不做**：未登录直接拦，需要账号会话 + 验证码处理 |

  **实现方案（P 级）**：
  1. Agent 工具 `open_webpage(url)` + `extract_page_text(selector?)`，内部封装 novel_browser 系列命令（open/navigate/execute_js）
  2. 默认提取策略 = 常见正文容器（`#chaptercontent` / `#content` / `.content` / `article`）命中即取；章节文本截断 3000-5000 字带回
  3. `read_url`（reqwest）作为 fallback——静态站直接抓 HTML 更快更省，novel_browser 留给 JS 渲染站
  4. **明确不做**：番茄字体解密、起点验证码、一切需登录/验证码/字体加密的站点——遇到直接返回「该站反爬无法读取」，不硬闯
  5. **产物**：Agent 把提取的章节文本带回研究结论卡，作为「同题材怎么开篇/节奏」的实证依据；研究 prompt 要求引用实际读到的内容，不许凭印象编

- 不动工坊/批量路径（工坊已有自己的新书逻辑）
- 不静默自动开局（新书必须用户参与）
- 不新造 UI 面板（方向选择/确认复用现有气泡确认流）
- 不重复造已有的能力（档案/角色卡/风格分析器/写前复盘都是现成的，只做组装）
